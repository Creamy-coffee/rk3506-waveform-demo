# 低频信号采集问题与改进建议

> 提交方：波形分析仪（RK3506 + Linux）软件侧
> 对象：FPGA 采集板（V32CAP3 协议）
> 日期：2026-10-20

---

## 一、一句话结论

**当前一帧固定 4096 个样点、按 65 MSPS 采集，只能覆盖 63 µs。
低于约 16 kHz 的信号，一帧里连一个完整周期都放不下** ——
主机再怎么放大/缩小都没用，因为数据里就没有。

解决办法只有一个：**FPGA 侧按需降采样（抽取），让一帧覆盖更长的时间**。
协议头里 `decimation` 字段早就留好了，但**目前没有真正生效**。

---

## 二、现象与数据

现场用 500 Hz 正弦测试，主机上只能看到一段弧线，凑不出一个周期。

| 项目 | 数值 |
|---|---|
| 帧长 | 4096 点 |
| 采样率 | 65 MSPS（每点 15.38 ns） |
| **一帧覆盖的时间** | **4096 × 15.38 ns = 63.0 µs** |
| 500 Hz 一个周期 | **2000 µs** |
| 一帧占一个周期的比例 | **3.2 %** |

按这个关系，**能看到完整周期的最低频率**是：

```
f_min = 1 / 63.0 µs ≈ 15.9 kHz
```

也就是说 16 kHz 以下（500 Hz、1 kHz、音频段）现在都看不到完整波形。

---

## 三、为什么会这样（不是软件 bug）

主机侧的缩放范围是：时间轴可以缩到 8 个采样点一屏（0.12 µs），
也可以放到整帧（63 µs）。**上限就是「一帧」**，因为再往外没有数据。

> 注：放大（看细节）是无限的，最小 0.12 µs；受限制的是缩小（看更长时间）。

---

## 四、协议现状

帧格式（小端，单帧 16428 字节）：

| 偏移 | 字段 | 类型 | 当前值 | 说明 |
|---|---|---|---|---|
| 0 | magic | 8 B | `V32CAP3!` | ASCII |
| 8 | version | u32 | 3 | |
| 12 | frame_id | u32 | 递增 | 帧序号 |
| 16 | Fs | u32 | 65000000 | **ADC 原始采样率，不要填抽取后的** |
| 20 | **decimation** | u32 | **1** | **抽取倍数（本次要用的字段）** |
| 24 | points | u32 | 4096 | 每帧样点数 |
| 28 | flags | u32 | 0 | 保留 |
| 32 | start_index_lo | u32 | | 本帧第一个样点在 ADC 流里的序号 |
| 36 | start_index_hi | u32 | | 高 32 位 |
| 40 | payload | 4096×2×i16 | | ch0/ch1 交错，每点 4 字节 |
| 16424 | crc32 | u32 | | 覆盖前 16424 字节 |

**已确认的问题**：参考实现 `raw_snapshot_uart.v` 里

```verilog
parameter integer PERIOD_CLKS=6500000, FS_HZ=65000000, DECIMATION=1,
...
5: header_word=DECIMATION;      // 只是把参数写进帧头
```

`DECIMATION` **只写进了帧头，没有参与实际采样** —— 采集仍然是 65 MSPS
逐点取，所以 dec 永远等于 1。（如果你们的工程里不是这样，请忽略这段并
直接按第五节加抽取即可。）

---

## 五、建议的改动（FPGA 侧）

### 5.1 核心：按 DECIMATION 真正丢点

采集缓冲仍然存 4096 点，但每个点之间间隔 `DECIMATION` 个 ADC 时钟：

```
对 k = 0..4095：
    buf[k] = adc_sample[ start_raw + k × DECIMATION ]
```

- 帧头 `decimation` 填实际倍数
- 帧头 `Fs` **仍然填 65000000**（主机自己算 `Fs/dec`）
- `start_index` 按**原始 ADC 样点**计数（即每帧前进 `4096 × dec`），
  诊断时更好和硬件时钟对照
- 一帧覆盖时间 = `4096 × dec / 65e6`

### 5.2 抗混叠（重要）

直接丢点会把高频内容折叠到低频，FFT 上会冒出假峰。
至少在丢点前做一次**平均**：

```verilog
// 最简：dec 点求和再右移（boxcar 平均）
// 更好：一级 CIC，或半带滤波级联
```

boxcar 平均的零点在 `Fs_eff` 的整数倍，第一旁瓣约 −13 dB，对示波器预览够用；
如果要做频谱分析，建议用 CIC（例如 5 级，抑制可到 −60 dB 以上）。

### 5.3 抽取倍率建议表

| dec | 等效采样率 | 一帧覆盖时间 | 能看完整周期的最低频率 |
|---|---|---|---|
| 1 | 65 MHz | 63 µs | 15.9 kHz |
| 2 | 32.5 MHz | 126 µs | 7.9 kHz |
| 4 | 16.25 MHz | 252 µs | 4.0 kHz |
| 8 | 8.125 MHz | 504 µs | 2.0 kHz |
| 16 | 4.06 MHz | 1.01 ms | 992 Hz |
| **32** | **2.03 MHz** | **2.02 ms** | **496 Hz** |
| 64 | 1.02 MHz | 4.03 ms | 248 Hz |
| 128 | 508 kHz | 8.06 ms | 124 Hz |
| 256 | 254 kHz | 16.1 ms | 62 Hz |

**建议支持 dec = 2^n，n = 0..8（1..256）**，覆盖 16 kHz ~ 62 Hz。
现场 500 Hz 的用例，**dec = 32** 正好一屏一个周期。

### 5.4 不需要改的部分

- 帧长仍 4096 点、帧格式不变 → 波特率 921600 下帧率仍是约 5.6 帧/秒
- CRC、magic、version 都不用动
- 主机侧已经就绪（见第七节）

## 六、验收标准

1. **回归**：dec = 1 时行为与现在完全一致（主机不需要任何操作）。
2. **500 Hz 用例**：dec = 32，输入 500 Hz 正弦
   - 主机示波器页「频率」读数 ≈ 500 Hz
   - 一屏（10 格）能看到约一个完整周期
   - FFT 峰值 ≈ 500 Hz，且没有明显假峰（说明抗混叠有效）
3. **切换**：运行中把 dec 从 1 切到 32（或反过来），主机应自动跟上，
   不需要重启程序。
4. **帧校验**：用附带的 `check_v32_frame.py` 检查抓到的原始数据，
   所有帧 CRC 通过、`decimation` 字段正确。

---

## 七、主机侧已完成的配套（无需 FPGA 再等）

已在主机固件里改好并通过验证（提交 `bd62165`）：

- 接受 `decimation` = 1..256 的 2 的幂（此前 `dec != 1` 会被判为头错误、整帧丢弃）
- 采样率自动改为 `Fs / dec` —— 时基、FFT 频率轴、波形类型判据全部自动跟随
- 时基档位从 0.5~10 µs/格 扩展到 **0.5~500 µs/格**

**验证结果**：用合成的 dec=32、500 Hz、4096 点（= 2.016 ms = 1 个周期）的帧
测试，主机正常接收，采样率自动变为 2.031 MSPS，FFT 峰值落在 496 Hz。
所以**FPGA 一改完，接上就能用**。

## 九、另一个现场观察（顺带反馈）

最近一次烧录后实测，帧率只有 **1.25 帧/秒**（正常应为 5.6 帧/秒）：
10 帧耗时 8 秒，而每帧 16428 字节在 921600 波特下只需 178 ms。
帧内容本身完全正确（CRC 全过），只是发送节奏慢了约 4.5 倍。
如果这是有意为之可以忽略；如果不是，建议一并查一下采集节拍/触发逻辑。

## 十、小结

| | |
|---|---|
| **问题** | 一帧 63 µs，低频信号（<16 kHz）看不到完整周期 |
| **根因** | 帧长固定、无抽取；协议里的 `decimation` 字段未生效 |
| **方案** | FPGA 按 `DECIMATION` 真正丢点（建议配 boxcar/CIC 抗混叠） |
| **主机动工** | 已完成，等 FPGA 的 `dec>1` 帧即可 |
| **关键参数** | 500 Hz 用 dec=32；建议支持 dec = 1..256（2 的幂） |

## 十一、追加需求：显示帧点数改为 1024（提升帧率）

### 背景

主机屏宽只有约 **740 像素**，现在送 4096 点是 **5.5 倍过采样**，
多出来的点显示不出来，却把带宽吃光了：

| 每帧点数 | 帧长 | 921600 波特下的帧率 |
|---|---|---|
| 4096（现在） | 16428 B | 5.6 帧/秒 |
| **1024（建议）** | **4140 B** | **22.3 帧/秒** |

### 要改的只有帧头的一个字段

**协议格式完全不变**，只是 `points` 填 1024、payload 相应缩短：

| 项 | 现在 | 改成 |
|---|---|---|
| `points`（偏移 24） | 4096 | **1024** |
| 单帧字节数 | 16428 | **4140**（= 40 + 1024×4 + 4） |
| CRC 覆盖范围 | 前 16424 字节 | **前 4136 字节** |
| 其余字段 | 不变 | 不变 |

主机侧已经支持 **256 / 512 / 1024 / 2048 / 4096** 任意 2 的幂点数，
**换回 4096 或改成 2048 都不用再改主机程序**。

### 关于 FFT

- 现阶段：FFT 仍由 RK3506 本地计算（**代码保留，未删除**）。
  用 1024 点时频率分辨率会降到 65 MHz/1024 ≈ 63.5 kHz；
  如果这一页需要更细的谱，可以让 FPGA 在这一页改发 4096 点（主机自适应，无需改程序）。
- 后续：FFT 计划移到 FPGA 端运算。为此帧头 `flags` 字段**预留 bit0**：
  `flags=1` 表示本帧 payload 是 FPGA 算好的频谱（格式待定，主机侧会按 flags 分流）。
  现在 `flags` 固定发 0 即可。
