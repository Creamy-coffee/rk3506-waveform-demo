V32CAP3 帧格式说明与本次修改点

面向：FPGA 采集板
目标：把显示帧从 4096 点改成 1024 点，把帧率从 5.6 提到 22
协议结构不变，只改 points 和对应的 payload 长度

二、本次要改的：只有三处

① 偏移 24：points 写 1024

// 原来
header_word = 4096;
// 改成
header_word = 1024;

② payload 只发 1024 个点

每点 4 字节（ch0 / ch1 各 2 字节，小端 int16，ch0 在前）：

for (k = 0; k < 1024; k = k + 1) begin
    tx_byte = ch0[k][7:0];   // ch0 低字节
    // 然后 ch0 高字节、ch1 低字节、ch1 高字节
end
// 共 1024 × 4 = 4096 字节

③ CRC32 覆盖范围改为前 4136 字节

CRC = crc32( frame[0 .. (40 + 1024*4 - 1)] )   // 前 4136 字节

CRC 用标准 CRC-32/ISO-HDLC（IEEE 802.3，多项式 0x04C11DB7 反射，

初值 0xFFFFFFFF，结果取反；等价于 Python 的 zlib.crc32）。

其余字段一律不动

magic、version、frame_id、Fs、decimation、flags、

start_index 全部保持原样。

start_index 建议仍按本帧第一个样点的绝对序号填，
每帧至少前进 points（1024）。

三、两个实例文件（可直接逐字节对照）

文件说明
frame_4096_now.bin现在的帧：4096 点，16428 字节
frame_1024_target.bin改完应有的帧：1024 点，4140 字节

两个文件里都是 1 MHz 正弦、两路数据（ch0 有信号、ch1 全 0），

帧头除 points/start_index 外完全一致，方便对照。

frame_1024_target.bin 前 48 字节

注意第 24 字节开始的那个 u32：现在是 00 10 00 00（=4096），

改完应该是 00 04 00 00（=1024）。

四、最容易踩的坑 ⚠️

只改帧头的 points、payload 还是发 4096 个点（16384 字节）—— 会直接失败。

主机是按 points 算帧长的：

帧长 = 40 + points*4 + 4

如果头里写 1024（帧长按 4140 算），实际却发了 16428 字节，

主机会从第 4140 字节处取 CRC 字段 —— 取到的是数据不是 CRC，

于是 CRC 校验失败 → 整帧丢弃 → 屏幕全黑。

头里的 points 和 payload 的实际点数必须一致。

五、怎么自检（改完请先跑一次）

把板子串口抓一段数据（或用逻辑分析仪导出），然后：

python check_v32_frame.py 抓包.bin

正确的输出应该是：

帧 #0   fid=7   ver=3 Fs=65000000 dec=1(→65.000 MSPS) pts=1024 start=4096
       一帧覆盖 15.8 µs
       CRC OK   ch0 -800..800  ch1 0..0

如果打印出 pts=4096，说明改动没生效（比特流没下载 / 改的不是发帧那个模块）。

如果 CRC 错误，多半是 payload 长度和 points 对不上。

校验脚本对帧长和 CRC 都会逐帧检查，会直接告诉你哪一项不对。
