# V32CAP3 帧格式说明与本次修改点

> 面向：FPGA 采集板
> 目标：把**显示帧**从 4096 点改成 1024 点，把帧率从 5.6 提到 22
> 协议结构**不变**，只改 `points` 和对应的 payload 长度

---

## 一、帧整体结构（小端 little-endian）

| 偏移 | 长度 | 字段 | 类型 | 取值 / 说明 |
|---|---|---|---|---|
| 0 | 8 | `magic` | char[8] | `V32CAP3!`（十六进制 `56 33 32 43 41 50 33 21`） |
| 8 | 4 | `version` | u32 | **3** |
| 12 | 4 | `frame_id` | u32 | 每帧 +1 |
| 16 | 4 | `Fs` | u32 | **65000000**（ADC 原始采样率，**不要填抽取后的**） |
| 20 | 4 | `decimation` | u32 | 1（如需抽取，填 2 的幂） |
| 24 | 4 | **`points`** | u32 | **本次修改点：4096 → 1024** |
| 28 | 4 | `flags` | u32 | 0（bit0 预留：payload 是频谱） |
| 32 | 4 | `start_index_lo` | u32 | 本帧第一个样点的 ADC 绝对序号（低 32 位） |
| 36 | 4 | `start_index_hi` | u32 | 高 32 位 |
| 40 | `points×4` | `payload` | i16[points×2] | **两路交错**：ch0[0], ch1[0], ch0[1], ch1[1] … |
| 40+`points×4` | 4 | `crc32` | u32 | 覆盖**前面全部字节**（不含自己） |

**单帧总长 = 40 + points×4 + 4**

| points | payload 字节 | 单帧总长 | 921600 下帧率 |
|---|---|---|---|
| 4096（现在） | 16384 | **16428** | 5.6 帧/秒 |
| **1024（改成）** | **4096** | **4140** | **22.3 帧/秒** |

---

## 二、本次要改的：只有三处

### ① 偏移 24：`points` 写 1024

```verilog
// 原来
header_word = 4096;
// 改成
header_word = 1024;
```

### ② payload 只发 1024 个点

每点 4 字节（ch0 / ch1 各 2 字节，**小端 int16**，ch0 在前）：

```verilog
for (k = 0; k < 1024; k = k + 1) begin
    tx_byte = ch0[k][7:0];   // ch0 低字节
    // 然后 ch0 高字节、ch1 低字节、ch1 高字节
end
// 共 1024 × 4 = 4096 字节
```

### ③ CRC32 覆盖范围改为前 4136 字节

```
CRC = crc32( frame[0 .. (40 + 1024*4 - 1)] )   // 前 4136 字节
```

CRC 用标准 **CRC-32/ISO-HDLC**（IEEE 802.3，多项式 0x04C11DB7 反射，
初值 0xFFFFFFFF，结果取反；等价于 Python 的 `zlib.crc32`）。

### 其余字段一律不动

`magic`、`version`、`frame_id`、`Fs`、`decimation`、`flags`、
`start_index` 全部保持原样。

> `start_index` 建议仍按**本帧第一个样点的绝对序号**填，
> 每帧至少前进 `points`（1024）。

## 三、两个实例文件（可直接逐字节对照）

| 文件 | 说明 |
|---|---|
| `frame_4096_now.bin` | **现在的**帧：4096 点，16428 字节 |
| `frame_1024_target.bin` | **改完应有的**帧：1024 点，4140 字节 |

两个文件里都是 1 MHz 正弦、两路数据（ch0 有信号、ch1 全 0），
帧头除 `points`/`start_index` 外完全一致，方便对照。

### `frame_4096_now.bin` 前 48 字节

```
00000000  56 33 32 43 41 50 33 21 03 00 00 00 07 00 00 00  V32CAP3!........
00000010  40 d2 df 03 01 00 00 00 00 10 00 00 00 00 00 00  @...............
00000020  00 10 00 00 00 00 00 00 00 00 00 00 4d 00 00 00  ............M...
```

### `frame_1024_target.bin` 前 48 字节

```
00000000  56 33 32 43 41 50 33 21 03 00 00 00 07 00 00 00  V32CAP3!........
00000010  40 d2 df 03 01 00 00 00 00 04 00 00 00 00 00 00  @...............
00000020  00 10 00 00 00 00 00 00 00 00 00 00 4d 00 00 00  ............M...
```

注意第 **24** 字节开始的那个 u32：现在是 `00 10 00 00`（=4096），
改完应该是 `00 04 00 00`（=1024）。

## 四、最容易踩的坑 ⚠️

**只改帧头的 `points`、payload 还是发 4096 个点（16384 字节）—— 会直接失败。**

主机是按 `points` 算帧长的：

```
帧长 = 40 + points*4 + 4
```

如果头里写 1024（帧长按 4140 算），实际却发了 16428 字节，
主机会从第 4140 字节处取 CRC 字段 —— 取到的是数据不是 CRC，
于是 **CRC 校验失败 → 整帧丢弃 → 屏幕全黑**。

**头里的 `points` 和 payload 的实际点数必须一致。**

## 五、怎么自检（改完请先跑一次）

把板子串口抓一段数据（或用逻辑分析仪导出），然后：

```bash
python check_v32_frame.py 抓包.bin
```

**正确的输出应该是：**

```
帧 #0   fid=7   ver=3 Fs=65000000 dec=1(→65.000 MSPS) pts=1024 start=4096
       一帧覆盖 15.8 µs
       CRC OK   ch0 -800..800  ch1 0..0
```

**如果打印出 `pts=4096`**，说明改动没生效（比特流没下载 / 改的不是发帧那个模块）。
**如果 `CRC 错误`**，多半是 payload 长度和 `points` 对不上。

校验脚本对帧长和 CRC 都会逐帧检查，会直接告诉你哪一项不对。
