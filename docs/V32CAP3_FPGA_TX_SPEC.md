# V32CAP3 数据帧格式规格（FPGA 发送端实现手册）

> 本文是**发送端**规格：FPGA 如何把双通道 ADC 采样打成帧、从 UART 吐出去。
> 接收端（Linux）已经按这份规格实现并跑通，任何一处不符会被整帧丢弃。
> 规格来源：`samples/real_frame_000001.bin`（真实采集帧，16428 B）逐字节反推 +
> 发送端参考 RTL `references/raw_snapshot_uart.v` 交叉核对。

## 1. 系统结构

```
AD9238 (双通道 12bit)
        │  65 MSPS
        ▼
   FPGA: 采样缓存 4096 点/通道  ──►  组帧  ──►  UART TX 921600 8N1
                                                    │
                                                    ▼
                                    RK3506 板 /dev/ttyS1  ──►  解析、CRC、绘图
```

- **单向**：只有 FPGA → Linux 的数据上传。**没有配置命令、没有 ACK、没有握手**。
  想改采样率/触发，得另外设计 RX 命令通道，那不属于本协议。
- **单帧内部连续**：4096 点真的是连续采样，时间轴 `t(i) = i / 65e6` 秒。
- **帧间是死区**：见 §6，这是物理限制。

---

## 2. 帧格式（权威表）

全部偏移从 0 开始；除魔数外均为 **little-endian（低字节先发）**。

| 偏移 | 长度 | 字段 | 类型 | 取值 / 含义 |
|---:|---:|---|---|---|
| 0 | 8 | `magic` | 字节串 | ASCII `"V32CAP3!"` = `56 33 32 43 41 50 33 21` |
| 8 | 4 | `version` | uint32 | **固定 3** |
| 12 | 4 | `frame_id` | uint32 | 采集帧号，每出一帧 +1，模 2³² 自然回绕 |
| 16 | 4 | `adc_fs_hz` | uint32 | **固定 65000000**（标称，未校准） |
| 20 | 4 | `decimation` | uint32 | **固定 1**（已抽点则为抽点比，接收端目前只认 1） |
| 24 | 4 | `points_per_channel` | uint32 | **固定 4096** |
| 28 | 4 | `flags` | uint32 | **固定 0**，未定义任何位 |
| 32 | 4 | `start_index_low` | uint32 | 本帧首点的 ADC 域时钟计数，低 32 位 |
| 36 | 4 | `start_index_high` | uint32 | 同上，高 32 位 |
| 40 | 16384 | `samples` | int16 ×2 ×4096 | 交错：第 i 组 CH0 在 `40+4i`，CH1 在 `42+4i` |
| 16424 | 4 | `crc32` | uint32 | 覆盖 `[0, 16424)`，低字节先发 |
| **合计** | **16428** | | | **无帧尾、无换行、无结束符、无尾部魔数** |

`start_index = (uint64(start_index_high) << 32) | start_index_low`。

它是**复位后的 ADC 时钟计数**（就是每个采样时钟 +1 的自由计数器），不是 Unix 时间、不是
绝对时刻。作用只有一个：让接收端判断帧与帧之间有没有重叠、有没有丢帧、间隔多久。

> **接收端会检查**：`start_index` 必须 ≥ 上一帧的 `start_index + 4096`，
> 且 `frame_id` 必须严格递增且差值 < 2³¹。所以**不要把同一批样点重复发两次**，
> 也不要让计数器清零（除非真的复位了，那要同时重建会话）。

## 3. 真实帧的逐字节样子

`samples/real_frame_000001.bin` 的前 48 字节：

```
偏移 00: 56 33 32 43 41 50 33 21   "V32CAP3!"        magic
偏移 08: 03 00 00 00               = 3                version
偏移 0C: 7C 00 00 00               = 124              frame_id
偏移 10: 40 D2 DF 03               = 65000000         adc_fs_hz   (0x03DFD240)
偏移 14: 01 00 00 00               = 1                decimation
偏移 18: 00 10 00 00               = 4096             points      (0x00001000)
偏移 1C: 00 00 00 00               = 0                flags
偏移 20: 71 A4 7B 54               = 1417389169       start_index_lo (0x547BA471)
偏移 24: 00 00 00 00               = 0                start_index_hi
偏移 28: F3 FF 03 00               CH0=-13 (0xFFF3), CH1=3 (0x0003)
偏移 2C: F2 FF 04 00               CH0=-14 (0xFFF2), CH1=4
...
末尾 8 字节: ... F2 FF 03 00 | 3F F5 19 5E
                              最后一组样点    CRC=0x5E19F53F
```

注意 `F3 FF` = 0xFFF3 = **−13**，第 12 位是符号位扩展到高 4 位（`F` 而不是 `0`）。
这就是最常见的坑：写成零扩展会变成 +65523，接收端直接判样点越界。

## 4. 样点编码

- ADC 输出 **12 位二进制补码**，范围 `−2048 .. 2047`。
- 存进帧里是 **int16**，必须 **符号扩展**：`{ {4{ch[11]}}, ch[11:0] }`。
- 两个通道**交错**存放，一组 4 字节，CH0 在前：

```
字节:  40+4i+0   40+4i+1 | 40+4i+2   40+4i+3
含义:  CH0[7:0]  CH0[15:8]  CH1[7:0]  CH1[15:8]
```

- 不是浮点、不是电压、不是两个 12 位挤进一个 16 位、不是先发 CH1。
- 若前端有 AC 耦合或运放，**帧里始终是 ADC 原始码值**，换算成 mV 是接收端的事。

## 5. CRC32

参数（标准的反射 CRC-32，等价 `zlib.crc32`）：

| 项 | 值 |
|---|---|
| 多项式（反射形式） | `0xEDB88320` |
| 初值 | `0xFFFFFFFF` |
| 输入反射 | 是（每字节先与寄存器低 8 位异或） |
| 输出反射 | 是（等价于整体反射） |
| 最终异或 | `0xFFFFFFFF` |
| 覆盖范围 | 字节 `[0, 16424)`：头部 40 B + 样点 16384 B |
| 存储方式 | uint32 小端，低字节先发 |
| 校验向量 | `crc32("123456789") == 0xCBF43926` |
| 空数据 | `crc32("") == 0x00000000` |

Verilog 逐字节实现（位宽无关，`crc` 保持 32 位）：

```verilog
function [31:0] crc_byte;
    input [31:0] c;
    input [7:0]  d;
    integer      k;
    reg   [31:0] v;
    begin
        v = c ^ {24'd0, d};
        for (k = 0; k < 8; k = k + 1)
            v = v[0] ? ((v >> 1) ^ 32'hEDB8_8320) : (v >> 1);
        crc_byte = v;
    end
endfunction
```

用法：每发一个字节就 `crc <= crc_byte(crc, byte);`，**头部和样点都要算，尾部不算**，
最后一帧样点发完后发 `~crc` 的 4 个字节（小端）。

> 这是 1 字节/8 拍的串行实现，在 921600 下一字节有 80 拍可用，绰绰有余。
> 想省时间也可以改成 256 项查表，但没必要，而且容易写错。

## 6. 时序与吞吐（必须理解，否则会设计错）

| 量 | 数值 |
|---|---|
| 单帧采样时间 | 4096 / 65 MHz = **63.015 µs** |
| 原始码率（双通道） | 65 M × 2 ch × 2 B = **260 MB/s** |
| UART 一帧线上时间 | 16428 B × 10 bit / 921600 = **178.26 ms** |
| 理论最高帧率 | 921600 / 10 / 16428 = **5.61 fps** |
| 实测（PC 端 Python 灌数据） | 4.9 ~ 5.0 fps（约 88% 线速） |
| 有效数据率 | 92160 B/s，只有原始码率的 **1/2820** |

**结论**：只能做"快照式"采集 —— 连续采 4096 点（63 µs）→ 停采 → 慢慢发 178 ms。
**不可能**拼成连续的 65 MSPS 流。想连续就得换 USB/千兆网/PCIe 或降低采样率。

所以 `FRAME_PERIOD`（两帧起始间隔）设多少都行：
- 设 6.5 M 拍（100 ms）→ 想 10 fps，但 UART 发不完，实际会被拖到 ~5.6 fps；
- 设 0 → 发完立刻采下一帧，仍是 ~5.6 fps。
反正瓶颈在 UART，不在帧周期。

## 7. 模块接口

建议的端口（参考实现 `rtl/v32cap3_tx.v` 就是这套）：

```verilog
module v32cap3_tx #(
    parameter integer POINTS       = 4096,
    parameter integer CLK_FREQ     = 65_000_000,   // clk 即 ADC 采样时钟
    parameter integer BAUD         = 921_600,
    parameter integer FS_HZ        = 65_000_000,
    parameter integer DECIMATION   = 1,
    parameter integer FRAME_PERIOD = 6_500_000     // 两帧起始间隔（拍）
)(
    input  wire               clk,
    input  wire               rst_n,
    input  wire               sample_valid,   // 连续采样时接 1'b1
    input  wire               fault,          // 采集异常，当前帧作废并重新开始
    input  wire signed [11:0] ch0,
    input  wire signed [11:0] ch1,
    output wire               tx,
    output wire               busy,
    output reg  [31:0]        completed,      // 已发帧数
    output reg  [31:0]        aborted,        // 作废次数
    output reg  [31:0]        skipped         // 跳过的样点数
);
```

`sample_valid` 用在 ADC 数据不是每拍都有效（比如降采样或分时复用）的场合；
纯连续采样直接接 `1'b1`，此时每个 `clk` 就是一个样点、`start_index` 就是拍数。

## 8. 状态机

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
     IDLE ──(timer==0 && sample_valid && !fault)──► CAP  (收 4096 点)
        ▲                                              │
        │                                              ▼
        │                                          (收满) frame_id++
        │                                              │
        │                                              ▼
        └────────────(尾 4B 发完)──────────── TAIL ◄── DATA ◄── HDR
                                                   │        (40B 边发边算CRC)
                                                   └── READ ◄─┘  空一拍取 RAM
```

要点（每条都对应一个真实的坑）：

1. **采样和发送互斥**。一帧没发完不能覆盖缓存，所以状态机在 `HDR/DATA/TAIL`
   期间不采新数据；采过的这一帧被"冻结"。
2. **CRC 边发边算**，不要先算一遍再发一遍——省一份遍历逻辑，也少一处错位风险。
3. **头部在发送期间必须冻结**。`frame_id`、`start_index` 在进入 `HDR` 前就定死，
   发送中途不许变（参考 RTL 里 `fault` 时明确不改 header 元数据）。
4. **`start_index` 取"本帧第一个样点"的计数器值**，不是发送时刻的值。
5. **block RAM 单写口**：首点用地址 0 直接写，其余按 `addr` 递增；
   别写成两个写口，某些综合器推不出 BRAM 会吃一堆 LUT。
6. **读 RAM 有一拍延迟**：`READ` 状态取字，下一拍才发 4 个字节。
7. **`frame_id` 在收满 4096 点时 +1**（此时代表"这一帧的编号已确定"），
   也可以在发送开始时 +1，只要单调递增即可。

## 9. UART 分频取值

`CLKS_PER_BIT = (CLK_FREQ + BAUD/2) / BAUD`（**四舍五入，不要直接整除截断**）：

| 系统时钟 | 精确分频 | 取整 | 实际波特率 | 误差 |
|---:|---:|---:|---:|---:|
| 24.0 MHz | 26.042 | 26 | 923077 | +0.16% |
| 50.0 MHz | 54.253 | 54 | 925926 | +0.47% |
| **65.0 MHz** | 70.530 | **71** | 915493 | **−0.66%** |
| 100 MHz | 108.507 | 109 | 917431 | −0.45% |
| 125 MHz | 135.634 | 136 | 919118 | −0.27% |
| 148.5 MHz | 161.133 | 161 | 922360 | +0.08% |
| 200 MHz | 217.014 | 217 | 921659 | +0.006% |

8N1 共 10 位，采样点在第 5 拍中点，误差 <1% 完全安全。
超过 ±1.5% 时改用分数分频（累加器：每拍加 `BAUD`，溢出即一个 bit 周期）。

### 9.1 换成 2000000（2 Mbps）时

板端 RK3506 的 UART1 时钟实测是 **32 MHz**（`/sys/kernel/debug/clk/clk_summary`
里 `sclk_uart1 = 32000000`），32 MHz / 16 = **正好 2.000 Mbps，分频系数 1，
零误差** —— 所以 2 Mbps 是这块板子不换时钟时的**上限**，4 Mbps 做不到。

帧时间从 178.26 ms 缩短到 **82.14 ms**，理论上限从 5.61 fps 提到 **12.17 fps**。

FPGA 侧只要把 `BAUD` 参数改成 2000000 重新算 `CLKS_PER_BIT`：

| 系统时钟 | 精确分频（2 Mbps） | 取整 | 实际波特率 | 误差 |
|---:|---:|---:|---:|---:|
| 24.0 MHz | 12.0 | 12 | 2000000 | 0% |
| 50.0 MHz | 25.0 | 25 | 2000000 | 0% |
| **65.0 MHz** | 32.5 | **33**（或 32） | 1969700 / 2031250 | −1.5% / +1.6% |
| 100 MHz | 50.0 | 50 | 2000000 | 0% |
| 125 MHz | 62.5 | 63（或 62） | 1984127 / 2016129 | −0.8% / +0.8% |

⚠️ **65 MHz 是这里唯一麻烦的时钟**：32.5 取整后误差 1.5%，已经压到 8N1 的边界。
如果 FPGA 主时钟就是 65 MHz，要么改用分数分频累加器，要么确认板上 UART
时钟另有来源（RK3506 的 UART 时钟和 ADC 采样时钟本来就是两回事 ——
ADC 65 MHz 是模拟前端给的，UART 走 32 MHz 的 sclk_uart1，两者不需要相等）。

**两端必须一致**。板端切换：

```sh
echo 2000000 > /etc/waveform_demo.baud     # 或 921600
/etc/init.d/S90waveform_demo restart
# 临时验证也可以直接： waveform_demo --source uart --baud 2000000
```

网页发送端在标题栏右侧的下拉框里选同样的速率（921600 / 2000000）。

## 10. 接收端会直接丢弃这帧的情况

实现完请逐条对照，这些全部是**整帧丢弃 + 重新搜魔数**，不会"部分接受"：

1. `version != 3`
2. `adc_fs_hz != 65000000`、`decimation != 1`、`points_per_channel != 4096`、`flags != 0`
3. 任一通道任一样点超出 `[-2048, 2047]`（典型原因：12→16 位**零扩展**而非符号扩展）
4. CRC 不符（典型原因：把尾部 4 字节也算进去了；或 CRC 的初值/最终异或漏了）
5. `frame_id` 与上一帧相同或倒退（重复发送同一帧）
6. `start_index` 比上一帧的 `start_index + 4096` 还小（窗口重叠）

另外：**长度必须恒为 16428**。多一个字节会让接收端把下一帧的魔数错位吃掉，
然后重新同步——现象是"能收到但帧率减半、丢包数飙升"。

## 11. 自检方法（强烈建议先做，再上板）

### 11.1 先用 Python 生成理想帧做对照

```python
import struct, zlib
POINTS = 4096
def build(ch0, ch1, frame_id, start_index):
    h  = b"V32CAP3!"
    h += struct.pack("<I", 3)            # version
    h += struct.pack("<I", frame_id)
    h += struct.pack("<I", 65000000)
    h += struct.pack("<I", 1)            # decimation
    h += struct.pack("<I", POINTS)
    h += struct.pack("<I", 0)            # flags
    h += struct.pack("<II", start_index & 0xFFFFFFFF, start_index >> 32)
    body = bytearray()
    for i in range(POINTS):
        body += struct.pack("<hh", ch0[i], ch1[i])   # CH0 在前
    pkt = h + bytes(body)
    assert len(pkt) == 16424
    return pkt + struct.pack("<I", zlib.crc32(pkt))

ch0 = [((i * 7) % 4096) - 2048 for i in range(POINTS)]   # 含负值，能抓符号扩展错误
ch1 = [2047 - i for i in range(POINTS)]                  # 全负斜坡
open("golden.bin", "wb").write(build(ch0, ch1, 777, 0x100001234))
```

### 11.2 仿真抓字节流

在 testbench 里用层次引用把真正发给 UART 的字节抓出来（不需要写 UART RX 模型）：

```verilog
integer fd = $fopen("sim_frame.bin", "wb");
always @(posedge clk)
    if (dut.sending && dut.tx_ready)
        $fwrite(fd, "%c", dut.byte_data);
```

为了跑得快，仿真时把 `CLK_FREQ` 设成和 `BAUD` 相等（`CLKS_PER_BIT=1`），
只验证**字节流内容**，不验证时序；时序留给上板看示波器。

### 11.3 自动判分

```python
import struct, zlib
d = open("sim_frame.bin", "rb").read()
assert len(d) == 16428, f"长度错了: {len(d)}"
assert d[:8] == b"V32CAP3!"
assert zlib.crc32(d[:-4]) == struct.unpack("<I", d[-4:])[0], "CRC 不符"
v = struct.unpack("<8I", d[8:40])
print("version,frame_id,fs,dec,pts,flags,lo,hi =", v)
print("成功：帧格式完全符合 V32CAP3")
```

### 11.4 上板联调

把 FPGA TX 接到板子 **JP4 引脚 10**（GND 接引脚 9），接收端已经跑着：
界面上 `Data Source /dev/ttyS1`、`Packet Loss 0 / N`、`Network Throughput ≈81 kB/s`
就说明通了。用示波器看 TX 脚，空闲应该是高电平，一帧 178 ms 的连续脉冲群。
